# ReproReady score

A static **reproduction-readiness** score for a paper's code artifact: how well a
submitted archive equips an independent researcher to regenerate the paper's
reported results, judged **without running any code**.

This page is the self-contained spec — the model, the grading rubric, the math,
and the scope and tier rules. Its companion
[implementation reference](implementation.md) is the code-faithful counterpart:
the exact detector thresholds, the routing table, the version stamps, and the
store schema. Read that page when the question is *what the code does*; read this
one when the question is *why*.

## What it measures

We adopt the [ACM definition of *artifact*](https://www.acm.org/publications/policies/artifact-review-badging):
a digital object created for or generated by the study — software, scripts, input
data, raw results, analysis code.

The ReproReady score measures **readiness**, not **executability**. It does not
predict whether the code would ultimately run; it measures whether the artifact
removes the manual effort a reproduction would otherwise cost.

The distinction is the line between readiness and correctness. A paper reports
three statistical plots and ships a `.zip` with one uncommented `solver.py`
(stdlib only) that prints three sets of numbers — no documentation, no mapping to
results. Even if the numbers are correct, a reproducer cannot confirm them without
reverse-engineering the axes, scales, and labels to turn numbers back into plots.
That removable effort is what the score measures.

**Artifact-only, by design.** The score reads the artifact's files — never the
manuscript PDF. Reproduction-relevant facts (dependency versions, hyperparameters,
run commands) written into a PDF are bad for everyone: authors must hand-sync them
as the code drifts, and a reproducer must hand-transcribe them. The score rewards
machine-readable information that lives with the code. The one manuscript-derived
fact it uses — whether the paper links a repo — is kept outside the score (see
[inclusion and the linked repo](#inclusion-and-the-linked-repo)).

## The model

A reproduction is a process that must pass through four **stages in series** —
every stage must succeed — where each stage can be carried by either of two
redundant **channels in parallel**. That is a series–parallel
[reliability block diagram](https://en.wikipedia.org/wiki/Reliability_block_diagram):
the system "reproduces" only if there is a working path from start to finish.

``` mermaid
flowchart LR
    START([start]) --> ENV
    ENV --> INP
    INP --> EXE
    EXE --> VAL
    VAL --> DONE([reproduced])
    subgraph ENV[Environment]
        direction TB
        E1[Implementation]
        E2[Documentation]
    end
    subgraph INP[Inputs]
        direction TB
        I1[Implementation]
        I2[Documentation]
    end
    subgraph EXE[Execution]
        direction TB
        X1[Implementation]
        X2[Documentation]
    end
    subgraph VAL[Validation]
        direction TB
        V1[Implementation]
        V2[Documentation]
    end
```

Read it as a chain of four blocks. Within a block the two channels sit in parallel
— either one carries the stage — so redundancy lives *inside* a stage. The blocks
sit in series, so all four are needed and the weakest stage governs the whole.

### Stages

| Stage | Asks | Satisfied by |
|---|---|---|
| **Environment** | Can I rebuild the software environment? | `requirements.txt`, `environment.yml`, lockfile, `Dockerfile`, version pins |
| **Inputs** | Can I obtain the data and configuration? | bundled `data/`, download script, dataset link, config / hyperparameter files |
| **Execution** | What do I run, and in what order? | `run_all.sh`, `main.py`, `Makefile`, a clear entry point |
| **Validation** | Did I reproduce the *right* thing? | result-named scripts (`table2.py`, `make_fig3.py`), bundled reference outputs |

### Channels

Each stage is carried by two channels, named for **who acts on the evidence**:

| Channel | Holds | What it is |
|---|---|---|
| **Implementation** | scripts, manifests, configs, lockfiles, data, notebooks, producers | a file a tool runs or ingests |
| **Documentation** | the README / prose | sentences a human reads |

The Implementation channel is the machine-actionable subset of the ACM artifact;
Documentation is the prose that shipped with it. Both are part of the artifact;
the channels split it by who acts on each. There is no imperative-versus-declarative
distinction — a pinned `Dockerfile` and an `install.sh` are equally
machine-actionable — so a producer script and a config file are both simply
*Implementation*.

Every file in the archive maps to the grid before grading:

- Junk and vendored paths (`.git`, `__pycache__`, `.DS_Store`, and the rest of
  `JUNK_DIRS` / `JUNK_BASENAMES`) are dropped first.
- The shallowest **renderable** `README` (extension `""`, `.md`, `.rst`, `.txt`,
  or `.markdown`) carries the **Documentation** channel — other prose does not.
- Every other file routes to **at most one** `(stage, Implementation)` cell by a
  first-matching rule.
- A file that matches **no** rule — a stray image, a PDF, a LICENSE, model weights
  — is simply not scored.

Result images are the one name-based exception: they reach Validation only when
named like a result (`fig*`, `table*`, `plot*`, `expected*`, …) or when they sit
in a `results` / `outputs` / `output` / `logs` directory; the `FIGURE_EXTS` list
is declared in the code but not wired into any rule. The full
[routing table](implementation.md#routing) gives the exact rule order.

**Why the Documentation channel is capped.** Prose must be read, interpreted, and
hand-executed — the largest human-error surface, and the one channel that does not
scale. So the Documentation channel is graded `0` or `0.5`, never `1`:
documentation can be *present and adequate* but never *fully reproduction-ready* on
its own. This puts "machine-actionable beats prose" directly into the grade, with
no per-channel weight or reliability coefficient. A stage met **only** by a strong
README therefore caps at `0.5`; the same stage met by a lockfile or a working
script reaches `1`.

## Grading

Every cell is graded `0 / 0.5 / 1` by **two checks, applied in order**, and the
two are decided differently:

- **Presence (`0 → 0.5`).** For the **Implementation** channel this is purely
  *structural*: a cell is present once at least one file routes to it, its bytes
  unread (the [routing table](implementation.md#routing) decides which files land
  where). For the **Documentation** channel it is a *content* scan: the README
  must actually document the stage — a keyword or section match on its text — so a
  README that merely exists is not enough.
- **Strength (`0.5 → 1`) — Implementation only** (Documentation caps at `0.5`). A
  present Implementation cell is promoted by a per-stage strength check (the
  `STRONG_CHECKS` registry in `rubric.py`). This is *mostly* a content read — a
  version pin, a real config, an entry point that shells out — but the strongest
  single artifacts short-circuit on presence alone: a `*.lock` file lifts
  Environment to `1`, and an orchestrator file (`Makefile` / `Snakefile` /
  `dvc.yaml`) or a pipeline-driver name (`run_all.py`, …) lifts Execution to `1`,
  both without reading bytes.

Two cells break the general shape. **Inputs** is the only cell that requires two
conditions *together* — obtainable data **and** a real config file — rather than
any single signal. **Validation** is the only stage that cannot reach `1` from
file evidence alone: its promotion is always the
[model call](#the-validation-model-call).

For Environment, Inputs, and Execution the `0.5 → 1` check is mechanical and
deterministic — a version pin, a non-empty config, a real orchestrator are all
syntactic, not semantic. Validation is the one genuinely semantic judgment, and
the only place a model is used.

For Environment, presence (`0.5`) is granted by routing alone — any one dependency
or container manifest, or an env-provisioning script, matches a rule — and the
separate `_env_strong` check then promotes `0.5 → 1` when a version is pinned (a
lockfile, `==` pins, a versioned conda env, or a pinned Docker base). A lockfile is
the limiting case: present by routing and strong by the lockfile branch, it reaches
`1` with no byte read. The exact forms are in the
[grading rubric](implementation.md#grading-rubric).

**The 4 × 2 grid.**

| Stage | Implementation `0.5` (present) | Implementation `1` (strong) — *deterministic test* | Documentation `0.5` (present, capped) |
|---|---|---|---|
| **Environment** | a manifest or env file exists | versions **pinned** — **one of:** a lockfile (`*.lock` / `Pipfile.lock`), `==` in `requirements*.txt`, a versioned `environment.yml` / conda env, a pinned Docker base (a tag or `@sha256`, never `:latest`), or `==` in `pyproject.toml` / `setup.{py,cfg}` | README has an install / setup / requirements section |
| **Inputs** | data referenced, *or* a config file exists | **both (a) and (b):** **(a)** data **obtainable** — *one of:* a download script, a non-trivial bundled `data/`, or a pointer file with a URL — **and (b)** a config with real values | README has a data / dataset / download section |
| **Execution** | runnable units exist (incl. bare computational modules) | a real **orchestrator** — **one of:** `run_all.sh` / `Makefile` / `dvc.yaml`, or an entry point that calls `subprocess`/`os.system` or imports sibling modules | README has a usage / run / quickstart section |
| **Validation** | result-named producers (`(fig\|table)\W*\d`) or output-writer calls (`savefig`/`to_csv`), or bundled `expected*` / reference outputs | producers plausibly target **specific numbered results** — [model-judged](#the-validation-model-call), not a checklist | README has a results / evaluation / figures section |

**Reading the strong column.** Each strength check combines its signals as a set
of alternatives: any single signal promotes the cell, and the check returns on the
*first* match while scanning *every file in the archive* — so the manifests need
not agree (an unpinned `requirements.txt` beside a `poetry.lock` still scores `1`,
the lock carrying it). Inputs is the exception: it needs both halves — obtainable
data **and** a real config — and they may come from *different* files (data from a
`download.sh`, the config from a separate `config.yaml`). Presence (`0.5`) is
always satisfied by a single signal; Validation's promotion to `1` is the single
[model judgment](#the-validation-model-call), not an enumerated test.

The exact constants behind each strength check — the pinning regexes, the
data-obtainable thresholds (`> 50 KB` of dataset bytes, or `≥ 3` data files, or an
acquisition script, or a URL-bearing pointer), the real-config test (`> 64`
characters, `≥ 2` non-comment body lines, a `:` or `=`), the orchestrator file and
name sets, and the per-stage README keyword lists — are tabulated in the
[grading rubric](implementation.md#grading-rubric).

**Weak-execution credit.** Bare computational modules (`model.py`, `losses.py`,
`metrics.py`, …) are the *substance being reproduced*, not instructions for
reproducing it. They count as runnable units — so the Execution Implementation cell
is present (`0.5`) and Execution is [in scope](#scope) — but `1` still requires a
real orchestrator the check can confirm. A code dump therefore caps at `0.5`.
Blanket credit for bare modules would not discriminate, since nearly every artifact
ships some script.

### The validation model call

The Validation `0.5 → 1` promotion is the only judgment that is semantic rather
than syntactic: *do these producers plausibly regenerate a specific numbered
result?* It is one model call per artifact, deliberately contained:

- **Manuscript-free.** The call judges *internal* correspondence — a producer named
  `fig2.py`, a `plt.savefig('fig2.pdf')` line, a README "Figure 2" mention — not
  coverage of the paper's actual result set. (Counting producers against the
  paper's actual result set is a possible extension, not part of the current
  score.)
- **Promote-only.** It can only lift the Validation Implementation cell `0.5 → 1`;
  it never prunes below the deterministic `0.5`. So `R` has a fully deterministic
  floor, and the model can only *raise* it — bounding both cost and reproducibility
  risk.
- **Fires only when present.** No producers means the Validation Implementation cell
  is `0` deterministically and **no call is made**. Many artifacts therefore score
  with no model in the loop at all.
- **Reproducible.** Fixed model, fixed prompt (versioned by `PROMPT_VERSION`),
  temperature 0, cached verdicts.

Everything else — all of Environment, Inputs, Execution, and the entire
Documentation channel — is deterministic code (basename plus content regex, parse,
or AST). Cost is roughly one small call per Validation-present artifact.

The system prompt asks one question: does **at least one** producer plausibly
regenerate a **specific numbered result** — a named "Figure N" or "Table N"? It
**promotes** when a producer ties to a numbered result (`fig2.py`,
`savefig('figure_2.pdf')`, `to_csv('results/table1.csv')`, a bundled
`results_table1.csv`, or a README line mapping a script to "Figure 2"); it
**keeps** the `0.5` for generic plotting with no numbered result (a `plot.py` loss
curve, a generic `evaluate.py` printing metrics, tensorboard logs, an unnamed
`results.csv`); and when unsure it keeps, since the deterministic floor already
credits a producer's presence. The input it sees is the Validation producer
basenames with their output-writing call-sites, plus the README's results slice —
no paper text, no other stages.

The exact prompt, the output schema, the context caps, and the detector IDs that
record each verdict live in the
[implementation reference](implementation.md#aggregation-and-validation). The prompt
is living documentation, not a frozen artifact: bumping `PROMPT_VERSION` re-runs
validation.

## The score

Two formulas, both standard, with **no weights and no reliability coefficients**.

**Within a stage (parallel channels).** The parallel-block, or noisy-OR, rule:

$$R_s \;=\; 1 - (1 - \text{Implementation}_s)\,(1 - \text{Documentation}_s).$$

A stage is at least as ready as its better channel, and redundancy pays with
diminishing returns: two `0.5` channels give `0.75` (more than a single `0.5`),
while a strong Implementation channel alone gives `1`. With the Documentation cap,
a documentation-only stage tops out at `0.5`.

**Across stages (series spine).** The equal-weight **geometric mean** over the
in-scope stages $\mathcal{S}$ (with $n = |\mathcal{S}|$):

$$\boxed{\,R \;=\; \Bigl(\textstyle\prod_{s \in \mathcal{S}} R_s\Bigr)^{1/n}\,}$$

This is the aggregation the **UN Human Development Index** adopted in 2010,
explicitly to stop a strong dimension from linearly compensating a weak one — it
embodies *imperfect substitutability* across dimensions
([UNDP technical note](http://data.un.org/_Docs/HDR%20Technical%20Notes.pdf)); the
[OECD/JRC handbook](https://knowledge4policy.ec.europa.eu/composite-indicators/toolkit_en/navigation-page/10-step-guide_en/step-7-aggregating-indicators_en)
frames it as the deliberate middle between fully-compensatory (arithmetic) and
fully non-compensatory (min) aggregation. It gives exactly the properties wanted:

| stage vector | arithmetic | **geometric** | raw product | min |
|---|---|---|---|---|
| `.9 .9 .9 .9` | .90 | **.90** | .66 | .90 |
| `.9 .9 .9 .5` | .80 | **.78** | .36 | .50 |
| `.9 .9 .9 0`  | .675 | **0** | 0 | 0 |

- **Calibrated:** if every stage equals `v`, then `R = v` (the raw product
  collapses good work just for the chain being long — `.9⁴ = .66`).
- **Non-compensatory:** a strong stage cannot buy back a weak one (the arithmetic
  mean lets a `0` survive at `.675`).
- **Hard floor:** any in-scope `R_s = 0 ⇒ R = 0` — a wholly unaddressed stage
  zeroes the score. This is the line between readiness and correctness from
  [what it measures](#what-it-measures), made arithmetic.

Equal weights mean there is nothing to tune: the `1/n` exponent *is* the
renormalisation over in-scope stages, so [scope](#scope) falls out of the formula
for free. (Alternative stage weightings and a min-versus-geometric comparison are
robustness checks, not the primary score.)

**The resulting bimodality is intended, not a defect.** Each graded stage is
`{0, 0.5, 1}`, and a stage is the noisy-OR of its channels (Documentation capped at
`0.5`), so the smallest non-zero stage value is `0.5`. With the hard floor this
makes `R ∈ {0} ∪ [0.5, 1]` — the `(0, 0.5)` band is **unreachable by
construction**. That is the readiness construct working: an artifact either
addresses every in-scope stage (a graded continuum in `[0.5, 1]`) or leaves one
wholly unaddressed (`R = 0`). Replacing the hard zero — with a small ε, a fixed
penalty for a missing stage, or an arithmetic mean — is **rejected**: each
re-introduces compensation (a strong stage buying back a missing one) and trades
construct validity for a smoother histogram. Such variants are kept only as
robustness diagnostics, never as the promoted score. What the `(0, 0.5)` emptiness
*does* break is the Tier 1 cut — a [tier](#tiers) labelling fix, not an `R` one.

## Scope

`R` is computed only over the stages an artifact actually exercises. Each stage is
in one of three states:

1. **In scope** — graded by the rubric. The default.
2. **Out of scope** — the artifact does not exercise the stage; drop it from
   $\mathcal{S}$ and let `1/n` renormalise. Neither rewarded nor penalised.
3. **In scope but unobservable to a static read** — drop from $\mathcal{S}$ and
   note it under [coverage](#coverage). An unknown is never scored as a failure.

Read per stage:

- **Environment** — always in scope (code always needs an environment).
- **Inputs** — in scope by default; out only for a *confirmed* self-contained
  artifact (no external data, no configs). An import-scan to confirm this
  automatically is parked.
- **Execution** — in scope only when the archive has **≥ 2 runnable units**
  (scripts, notebooks, or computational modules); a one-file artifact has nothing
  to orchestrate beyond running itself.
- **Validation** — always in scope (the paper reports results to check against).

This is what handles the dataset or census paper that ships data with little or no
code: the stages it does not exercise simply leave $\mathcal{S}$, rather than
forcing `R = 0`.

**False zeros.** An in-scope stage that is merely *not statically observable* can
be mis-graded `0` (a *false zero*) instead of being dropped under state 3 — making
`R = 0` assert "wholly unaddressed" when the truth is "unknown to a static read".
Honouring state 3 (unobservable ⇒ **dropped**, not failed) is the only correction
that legitimately moves an `R` value, and only because the prior value was wrong.
Genuinely empty stages (observably no Implementation, no Documentation) stay `0`,
so the fix is a targeted correction, not a rescore. The true Inputs zeros that
*are* recoverable — a named public dataset, shipped weights, a config a static read
misses — are addressed separately by additive Inputs detectors that *raise* a cell,
never reshape `R`.

## Tiers

An ordinal, ACM-badge-style label read off the final score. Because
[the score](#the-score) fixes the support to `R ∈ {0} ∪ [0.5, 1]`, the ordinal
bands are cut onto that **real support** (the re-cut, stamped
`TIER_SCOPE_VERSION = "tier-scope-v1"` in `reproready.aggregate.PROMOTED_CONFIG`):

| Tier | Name | Condition |
|---|---|---|
| N/A | Not applicable | no code (the logical-PDF rule; see [inclusion and the linked repo](#inclusion-and-the-linked-repo)) |
| 0 | Incomplete | `R = 0` — some in-scope, observable stage wholly unaddressed |
| 1 | Minimal | `0.5 ≤ R < 0.66` |
| 2 | Solid | `0.66 ≤ R < 0.80` |
| 3 | Robust | `R ≥ 0.80` |

The band edges `(0.66, 0.80)` (`aggregate.TIER_RECUT_CUTS`) are chosen against the
observed distribution of scores so that all four bands populate; `R` itself is
identical to the pre-re-cut scorer (the re-cut is a pure relabel of the same `R`).
A stage is **redundant** when *both* its channels are ≥ `0.5`; redundancy is
reported as metadata beside the tier and no longer decides any tier — Tier 3 is a
pure `R ≥ 0.80` band.

**History.** The original cut placed Tier 1 in `0 < R < 0.5`, a band that is
[empty by construction](#the-score), so the tiers came out `{0, 2, 3}` with an
empty Tier 1. The re-cut above fixes that labelling artifact without touching `R`;
paired with the false-zero scope fix, the promoted config populates all four tiers.

## Coverage

Reported as plain metadata beside `R`, not a scored symbol: **how many in-scope
stages were visible to a static read** (for example, "scored 3/4 stages; README
unparseable"). It qualifies `R` — low coverage means the score saw less of the
story — but does not change it. Coverage drops when a stage is unobservable
([scope](#scope), state 3), when the README is present but unparseable (the
Documentation channel goes dark), or when a thin archive is paired with an
un-crawled linked repo (see
[inclusion and the linked repo](#inclusion-and-the-linked-repo)).

## Inclusion and the linked repo

**Inclusion.** The score is computed only for artifacts that contain code. An
archive that is a **logical PDF** (a filtered inventory of exactly one `.pdf`) or
otherwise has no source files gets tier **N/A** and no score.

**Time-invariance.** A pinned lockfile scores `1` whether submitted in 2011 or
2024. Software *decay* (a 2011 `requirements.txt` that no longer resolves) is real,
but it is a property of the world, not the artifact; baking it in would confound
"authors improved" with "old artifacts rotted", and confuse any analysis of how
artifacts change over time. Decay is studied separately. It is also why redundancy
is rewarded — spare channels are what survive decay.

**The linked repository.** Whether a paper links a code repo is kept **out of**
`R`: a linked repo is usually the *same code* as the archive, so folding it in
would double-count. It is handled outside the score — recorded as a binary
covariate (does the paper link a repo?), and optionally scored *in parallel* on the
cloned repo, reported beside the archive score and **never fused**, since their gap
is itself a finding. (A 2026 clone of a 2014 paper's repo is "readiness today", and
is noted as such.)

## Worked examples

**Example A — a mid-quality archive.** Unpinned `requirements.txt`; README lists
deps in prose; bundled `data/` but a boilerplate config; README names the dataset;
`main.py` plus modules but no clear orchestrator; README has a run command; a
generic `plot.py` with no specific-result correspondence; no results section.

| Stage | Implementation | Documentation | $R_s$ |
|---|---|---|---|
| Environment | 0.5 (unpinned) | 0.5 | `1 − .5·.5 = 0.75` |
| Inputs | 0.5 (data only, config boilerplate) | 0.5 | `0.75` |
| Execution | 0.5 (modules, no orchestrator) | 0.5 | `0.75` |
| Validation | 0.5 (generic producer, no promotion) | 0 | `0.5` |

$R = (0.75 \cdot 0.75 \cdot 0.75 \cdot 0.5)^{1/4} \approx \mathbf{0.68}$ →
**Tier 2 (Solid)**. Every stage is addressed and three are redundant, but the
generic, unmapped Validation caps the score below Robust.

**Example B — the lone self-contained script.** One `solver.py` emitting three
tables; README says only "Requirements: numpy, scipy" and "Run: `python
solver.py`".

- One runnable unit → **Execution out of scope**; $\mathcal{S} = \{E, I, V\}$,
  $n = 3$.
- Environment: deps named in prose only → Implementation `0`, Documentation `0.5` → $R_E = 0.5$.
- Inputs: no data, no config, README silent → $R_I = 0$.
- Validation: `to_csv` present but generic, no mapping → $R_V = 0.5$.

$R = (0.5 \cdot 0 \cdot 0.5)^{1/3} = \mathbf{0}$ → **Tier 0 (Incomplete)**,
vector `(0.5, 0, n/a, 0.5)`. The script may *execute*, but a reproducer cannot
statically confirm its inputs — the hard floor of [the score](#the-score).

## Notation

| Symbol | Meaning |
|---|---|
| Environment, Inputs, Execution, Validation | the four stages, in series (see [the model](#stages)) |
| Implementation, Documentation | the two channels, in parallel; Documentation capped at `0.5` (see [the model](#channels)) |
| $R_s$ | stage readiness — noisy-OR of its two channels (see [the score](#the-score)); the diagnostic vector $(R_E, R_I, R_X, R_V)$ |
| $\mathcal{S}$, $n$ | the in-scope stages and their count (see [scope](#scope)) |
| $R$ | **ReproReady score** — equal-weight geometric mean of $R_s$ over $\mathcal{S}$ (see [the score](#the-score)); $R \in [0,1]$ |
| Tier | ordinal label N/A / 0 / 1 / 2 / 3 from `R` plus redundancy (see [tiers](#tiers)) |
| coverage | how many in-scope stages a static read could see — metadata, qualifies `R` (see [coverage](#coverage)) |
